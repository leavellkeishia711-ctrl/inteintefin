# FinanceIntel — Дополнение к PRD v2.0 (Аддендум v2.1)

Этот документ содержит **только новые/уточнённые решения** по трём пунктам из последнего раунда обсуждения. Он не заменяет `FinanceIntel_PRD_v2.md`, а дополняет его — по каждому пункту указано, к какому разделу основного документа относится изменение.

---

## Дополнение 1. SLA-эскалация — финализация

**Дополняет:** раздел 13, строка 13.3 («SLA на модерацию»); модуль 6.7 (пайплайн Market Intelligence).

**Было:** логика была предложена как дефолт с пометкой "требует подтверждения".

**Стало (финальное решение):** логика подтверждена без изменений и переходит из статуса "предложение" в статус "решение".

**Полная финальная логика жизненного цикла черновика поста:**

```
draft → pending_review
           |
           ├── модератор принимает решение за 72ч → approved / rejected
           |
           └── 72ч истекли без решения → expired (не публикуется)

Напоминания модераторам: через 24ч и через 48ч после
создания черновика (до истечения срока).
```

**Технические следствия:**
- В `ai_generated_posts.status` добавляется значение `expired` (полный список: `draft / pending_review / approved / rejected / expired / published`).
- Нужен фоновый scheduled job (Celery beat или аналог), который раз в час проверяет очередь `pending_review` и: (а) шлёт напоминание модератору при достижении 24ч и 48ч, (б) переводит пост в `expired`, если истекли 72ч.
- Записи `expired` остаются в базе (для аналитики: сколько сигналов "протухает" не будучи рассмотренными — это само по себе полезная метрика загрузки модераторской команды) и попадают в Audit Log (6.11).

## Дополнение 2. Общая лента vs персонализация по вертикалям — уточнение правила

**Дополняет:** раздел 5 (архитектура), модуль 6.7 (ветка A — публичная лента), раздел 8.2 (схема БД), раздел 13, строка 13.2.

**Было:** общее правило — контент производится и модерируется один раз, но каждый клиент видит только то, что релевантно его вертикалям через `company_vertical_watchlist`. Не было разделения на "общие" и "вертикальные" темы.

**Стало (финальное решение):** правило распределения публичной ленты зависит от типа темы:

| Тип сигнала | Кому показывается |
|---|---|
| Общерыночная тема (не привязана к конкретной вертикали — например, глобальное изменение политики рекламной платформы, общее ужесточение анти-фрод правил) | Всем клиентам с активной подпиской на Market Intelligence, независимо от их watchlist |
| Вертикально-специфичная тема (например, "блокировки Gambling-аккаунтов в EU") | Только клиентам, у которых соответствующая вертикаль/гео есть в `company_vertical_watchlist` |

**Технические следствия:**
- Поле `detected_patterns.vertical` становится явно nullable: `NULL` = общерыночный сигнал (широковещательная рассылка), заполненное значение = таргетированная рассылка по watchlist.
- Логика публикации (шаг 8 пайплайна 6.7, ветка A) при `approved`:
  ```
  IF pattern.vertical IS NULL:
      публикуется всем компаниям с активной MI-подпиской
  ELSE:
      публикуется компаниям, где pattern.vertical есть в
      их company_vertical_watchlist
  ```
- UI-следствие: в ленте имеет смысл выделить два визуальных блока — "Рынок в целом" (общие темы) и "По вашим вертикалям" (таргетированные), чтобы пользователь понимал природу каждого сигнала.
- Ветку B (персональные impact-брифы) это правило не затрагивает — они по определению всегда привязаны к конкретной компании и её кампаниям, вопрос "общее/вертикальное" для них не применим.

## Дополнение 3. Технический доступ к Telegram — финализация

**Дополняет:** модуль 6.7 (сбор источников), раздел 11 (технологический стек), раздел 13, строка 13.8.

**Было:** гибридный подход был предложен как рекомендация.

**Стало (финальное решение):** гибрид подтверждён как архитектурное решение:

- **Bot API** — для источников, добавленных вручную куратором (низкий риск блокировки, но работает только там, куда бот приглашён администратором чата).
- **Клиентский доступ (Telethon/MTProto-подход)** — читающий аккаунт для автообнаружения новых публичных каналов/чатов, с обязательными ограничениями частоты запросов, чтобы снизить риск блокировки аккаунта.

**Технические следствия:**
- В раздел 11 (стек) добавляется строка: **Telegram-доступ** — `aiogram` / `python-telegram-bot` (Bot API) + `Telethon` (клиентский режим для автообнаружения).
- Рекомендуемые эксплуатационные ограничения для клиентского аккаунта: консервативный лимит запросов в минуту, постепенное (не массовое) вступление в новые чаты, использование выделенного сервисного номера (не личного аккаунта сотрудника).
- Поскольку клиентский аккаунт может быть ограничен или заблокирован платформой, это состояние должно отслеживаться модулем **Data Quality Monitoring (6.15)** — при потере доступа система должна генерировать алерт вида "Telegram reader account rate-limited/заблокирован", а не молча переставать собирать данные.
