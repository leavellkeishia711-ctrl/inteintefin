## 1. Executive Summary

FinanceIntel — SaaS-платформа финансовой разведки и управления для медиабаинговых компаний в сфере performance-маркетинга и арбитража трафика. Объединяет финансовый учёт, cash flow, аналитику рекламной эффективности, AI-анализ причин и AI-мониторинг внешних рыночных сигналов с прогнозом их влияния на бизнес.

## 2. Видение продукта: от MVP до зрелой платформы

### 2.1 North Star

FinanceIntel становится финансовой операционной системой рынка performance-маркетинга: единой точкой, где владелец медиабаинговой компании в любой момент точно знает, сколько денег у бизнеса, куда движется рынок и какое решение принять — без ручной сверки таблиц и без необходимости лично мониторить десятки Telegram-чатов.

MVP (описан в разделе 10) — это первый рабочий срез этой системы, а не весь продукт. Ниже — куда он растёт дальше.

### 2.2 Целевое состояние продукта (полная функциональность)

**A. Финансовое ядро**
- Мультивалютность, консолидация нескольких юрлиц/брендов под одной "холдинговой" учётной записью
- Автоматическая сверка банковских транзакций с внутренними записями (reconciliation)
- Экспорт данных для бухгалтерии/налоговой отчётности

**B. Маркетинговая аналитика**
- Полное покрытие всех крупных рекламных платформ, трекеров, партнёрских сетей
- Предиктивное определение "выгорания" креативов
- Полуавтоматическое перераспределение бюджета между кампаниями на основе ROI-трендов (с подтверждением пользователя)

**C. Market Intelligence (зрелая версия)**
- Гибридный сбор источников: ручная курация + автообнаружение новых каналов/чатов (см. 6.7 и решение 13.8)
- Двухуровневая лента: публичная модерированная + персональные немодерированные impact-брифы (см. решение 13.2)
- Адаптивное определение значимости сигнала (baseline-deviation вместо фиксированного порога — см. 13.7)
- Reliability score источников, накопленный за месяцы работы — становится проприетарным активом платформы
- Industry benchmarking: сравнение показателей клиента со средними по платформе в его вертикали (агрегированные анонимизированные данные — работает только при достаточном числе клиентов)

**D. AI-слой**
- AI Financial Analyst становится проактивным — сам инициирует уведомления ("Обрати внимание, я заметил...."), а не только отвечает на вопросы
- Scenario Modeling с симуляциями по множеству случайных сценариев для сложных what-if вопросов
- Рекомендации по бюджету, учитывающие рыночные сигналы напрямую

**E. Платформенные/enterprise возможности**
- Публичный API для интеграции с внутренними инструментами клиента
- White-label версия для крупных агентств
- Мобильное приложение с push-уведомлениями
- Мультикомпания/агентская модель (один аккаунт управляет несколькими брендами)
- Сертификации безопасности (например, SOC 2) для работы с крупными клиентами

**F. Бизнес-модель зрелой платформы**
- Базовый тариф (по объёму spend/выручки) — Dashboard, P&L, Cash Flow, AI Analyst
- Market Intelligence — отдельный платный add-on (решение 13.9), с уровнями доступа (публичная лента / персональные брифы)
- Долгосрочно: продажа агрегированной анонимизированной рыночной аналитики как отдельного продукта для более широкого рынка (агентства, рекламные платформы)

**G. Конкурентное преимущество (moat)**
Сами по себе публичные источники данных не эксклюзивны — любой конкурент может их читать. Защищённость продукта строится на другом:
1. Накопленная история точности прогнозов и reliability score источников — не копируется быстро.
2. Сетевой эффект от объёма клиентских данных для бенчмаркинга.
3. Глубина интеграции с финансовыми данными клиента — переключение на другой инструмент становится дорогим (data lock-in).

## 3. Проблема рынка

Данные медиабаинговых компаний разбросаны между рекламными кабинетами (Meta, Google, TikTok), трекерами (Keitaro, Voluum, Binom), партнёрскими сетями (Affise и др.) и финансовыми таблицами (Excel/Google Sheets). Из-за этого у владельца нет единой картины: сколько компания реально заработала, хватит ли денег на дальнейшую работу, какие команды эффективны, и какие внешние события могут ударить по прибыли до того, как это произошло.

## 6. Функциональные модули

### 6.1 Financial Dashboard
Revenue, Expenses, Profit, Margin, ROI, ROAS, Cash Balance, Finance Health Score (0–100).

### 6.2 P&L Management
Доходы (партнёрские выплаты, продажи, прочее) минус расходы (реклама, зарплаты, инфраструктура, операционные). Показывает, прибыльна ли компания или просто прогоняет оборот.

### 6.3 Cash Flow Management
Движение денег во времени, ключевая метрика — Cash Runway.
```
Баланс: $500 000 · Средний расход: $20 000/день · Runway: 25 дней
```

### 6.4 Campaign Financial Analytics
Интеграция с Keitaro/Binom/Voluum/Meta/Google/TikTok. Не просто цифры (spend, ROI, ROAS, CPA, CPM) — а поиск причин их изменения.

### 6.5 Team Performance Analytics
ROI, стабильность и риск-профиль по байерам, командам, тимлидам.

### 6.6 AI Financial Analyst
Диалоговый ассистент с доступом к P&L, Cash Flow, кампаниям и рыночным сигналам.

### 6.7 Market Intelligence AI — двухуровневая модель

**Источники (MVP):** заранее курируемый список Telegram-чатов, форумов (BlackHatWorld, Reddit), новостных каналов — загружаются вручную.

**Пайплайн:**
```
1. INGESTION       Сбор сырых сообщений из источников
2. PREPROCESSING   Дедупликация, язык, фильтрация спама, теги (вертикаль/гео)
3. PATTERN DETECTION   Поиск значимых кластеров упоминаний (см. решение 13.7)
4. RISK SCORING    Вероятность + потенциальное влияние на финансы
        |
        ├── ВЕТКА A: Публичная лента (модерируется)
        |     5. Draft generation → 6. Human Review Queue →
        |     7. Approve/Reject → 8. Публикация всем подписанным
        |     клиентам (отфильтровано по их watchlist вертикалей)
        |
        └── ВЕТКА B: Персональный impact-брифы (НЕ модерируется)
              5. Для каждой подписанной компании: сопоставление
              паттерна с её активными кампаниями/вертикалями
              6. Мгновенная генерация: какие кампании затронуты,
              оценка финансового влияния, рекомендация
              7. Доставка управленцу (Owner/CEO/CFO/Team Lead)
              с обязательным постоянным UI-дисклеймером:
              "Этот анализ не проходит модерацию, ИИ может
              ошибаться/галлюцинировать, платформа не несёт
              ответственности за решения на его основе"
```

**Почему две ветки:** публичная лента даёт проверенные, качественные рыночные алерты для всех клиентов сразу (экономия на модерации — один пост проверяется один раз). Персональный брифы дают управленцам мгновенную, специфичную для их бизнеса интерпретацию сигнала — без задержки на очередь модерации, но с явным предупреждением о рисках такого контента.

**Определение значимости сигнала (порог для Pattern Detection) — варианты:**

| Вариант | Как работает | Когда применять |
|---|---|---|
| A. Фиксированный порог | N упоминаний темы за T часов (например, ≥30 упоминаний за 24ч из ≥3 разных источников) | MVP — просто, предсказуемо, легко настроить вручную |
| B. Адаптивный (baseline deviation) | Сравнение текущей частоты упоминаний с historical-средним по этой теме/вертикали (например, отклонение более чем на 2–3 стандартных отклонения от 14-дневного среднего) | После накопления данных — не требует ручной перенастройки порогов под каждую тему |
| C. Взвешенный по надёжности источника | Сумма (упоминания × reliability_score источника) должна превысить порог — несколько надёжных источников триггерят так же, как много случайных | Зрелая версия, после внедрения reliability scoring |

**Рекомендация:** старт MVP с варианта A, переход на B/C по мере роста (см. roadmap 2.3).

**Reliability score источников:** каждый источник (`intelligence_sources`) получает числовую оценку надёжности (0–100). Стартовое значение выставляется вручную при добавлении источника, далее корректируется по итогам feedback loop (см. ниже).

**Feedback loop:** после публикации поста система (в автоматическом режиме, силами AI — решение 13.7) сверяет, подтвердился ли прогноз, и на основе этого корректирует `reliability_score` источников, участвовавших в сигнале. Рекомендация: раз в месяц — лёгкая выборочная проверка человеком результатов самооценки AI, просто как контроль качества (не полноценная модерация, а спот-чек), поскольку иначе AI оценивает сам себя без внешней проверки.

**Технический доступ к источникам (Telegram):** гибридный подход — официальный Bot API для вручную добавленных чатов/каналов (низкий риск блокировки, но работает только там, где бот добавлен), плюс аккуратный клиентский доступ (в духе Telethon/MTProto) с консервативными лимитами частоты запросов — для автообнаружения новых публичных каналов.

**Объём сообщений и бюджет на LLM-обработку — рамочный расчёт:**
1. Сырой поток: (число источников) × (среднее сообщений/день). Для MVP с ~20–30 источниками — ориентировочно 3 000–15 000 сообщений/день (закрытые чаты арбитражников бывают очень активны).
2. Дешёвый предфильтр (ключевые слова + лёгкая классификация, не через дорогую LLM) отсекает ориентировочно 90%+ шума → остаётся ~300–1 500 кандидатов/день.
3. Кластеризация/дедупликация кандидатов в паттерны — десятки кластеров/день.
4. Только кластеры, прошедшие порог значимости (см. таблицу выше), доходят до дорогой модели для финальной генерации черновика — единицы/до пары десятков в день на MVP-масштабе.

Рекомендация: в первые недели MVP плотно отслеживать реальный расход на LLM API и калибровать агрессивность предфильтра — архитектура "дешёвый фильтр → дорогая модель только в конце" стандартна именно для контроля стоимости.

### 6.8 AI Content Intelligence
Регулярные аналитические материалы (обзоры, дайджесты) — идут по той же публичной ветке с модерацией, что и точечные алерты (6.7, ветка A).

### 6.9 Forecasting Engine
Прогноз финансов компании на основе внутренних данных (P&L, Cash Flow), опционально комбинируется с сигналами Market Intelligence.

### 6.10 Decision Recommendation Engine
Конкретные рекомендации по действиям на основе анализа. Рекомендации, построенные на данных публичной ленты (модерированной), считаются надёжными; рекомендации на основе персональных impact-брифов наследуют их статус "без модерации".

### 6.11 Audit Log
История изменений бюджета/расходов/прогнозов, а также лог решений модерации (кто одобрил/отклонил какой пост).

### 6.12 Budget Planning
Планирование бюджета по каналам с проверкой на безопасность относительно ликвидности.

### 6.13 Scenario Modeling ("What-if")
Моделирование последствий гипотетических решений (бюджет, гео) до их принятия.

### 6.14 Alerts System
Уведомления в Telegram/Email — включая как публичные модерированные алерты, так и персональные impact-брифы (с соответствующей маркировкой).

### 6.15 Data Quality Monitoring
Контроль полноты и актуальности данных ("Meta Ads не обновлялись 8 часов").

## 8. Модель данных (Database Schema)

### 8.1 Базовые таблицы
`users(id, name, email, company_id, role, created_at)`
`companies(id, company_name, balance, currency, created_at)`
`transactions(id, company_id, type, category, amount, date, created_by)`
`campaigns(id, company_id, source, platform, geo, vertical, spend, revenue, roi, date)`
`alerts(id, company_id, type, risk_level, message, source_post_id, date)`

### 8.2 Таблицы Market Intelligence
`intelligence_sources(id, type, name, handle_or_url, vertical_tags[], reliability_score, status, added_by, created_at)`
`raw_signals(id, source_id, content_hash, raw_text_ref, language, detected_at, matched_keywords[])`

`moderation_log(id, post_id, moderator_id, action, comment, timestamp)`
`impact_briefs(id, pattern_id, company_id, body, generated_at)` — персональная ветка, без статуса модерации
`company_vertical_watchlist(company_id, vertical, geo, created_at)` — используется и для фильтрации публичной ленты, и для триггера персональных брифов
`forecast_accuracy(id, post_id, outcome_confirmed, actual_impact, reviewed_at)`

## 12. Нефункциональные требования

- **Безопасность:** шифрование финансовых данных, RBAC, защита API-ключей интеграций.
- **Ответственность за контент:** платформа не несёт ответственности за решения, принятые на основе AI-аналитики — это фиксируется в пользовательском соглашении (решение 13.6). Отдельно и явно (в интерфейсе, не только в тексте соглашения) помечаются персональные impact-брифы как немодерированный AI-контент.
- **Юридический статус источников:** данные собираются из открытых источников (решение 13.5). Отметим: "открытый" источник снижает часть рисков, но не обязательно отменяет ограничения на автоматический сбор в пользовательских соглашениях самих площадок (Telegram, форумы) — это не юридическая консультация, а факт, который стоит один раз сверить с юристом перед масштабированием сбора данных, а не блокирует запуск.
- **Масштабируемость:** асинхронный пайплайн обработки сообщений с контролем стоимости LLM (см. 6.7).
- **Хранение данных:** политика удержания `raw_signals` — определить срок хранения сырых данных.

| # | Вопрос | Решение |
|---|---|---|
| 13.1 | Приоритет Market Intelligence в roadmap | Остаётся Фаза 4 (Месяц 4), как и планировалось изначально |
| 13.2 | Модель модерации | Двухуровневая: публичная лента модерируется человеком и видна всем подписанным клиентам (отфильтровано по вертикали); управленцы дополнительно получают персональные немодерированные impact-брифы с обязательным дисклеймером о непроверенности и отсутствии ответственности платформы |
| 13.3 | SLA на модерацию | 3 суток на решение. По умолчанию: если решение не принято за 3 суток — черновик автоматически снимается с публикации (не публикуется), модераторам шлются напоминания на 24ч/48ч. *(предложенный дефолт — подтвердите или скорректируйте)* |
| 13.4 | MVP-версия Market Intelligence | Упрощённая: ручная загрузка источников, без автопарсинга — подтверждено |
| 13.5 | Юридический статус источников | Данные собираются только из открытых источников; юридических рисков не предполагается. Рекомендация: разовая сверка с юристом перед масштабированием — не блокирует запуск |
| 13.6 | Ответственность за контент | Платформа ответственности не несёт — фиксируется в пользовательском соглашении. Поштучная маркировка "не финансовая консультация" на каждом посте публичной ленты не требуется (покрывается соглашением). Для персональных impact-брифов маркировка о немодерированности — обязательна и находится в самом интерфейсе (решение 13.2) |
| 13.7 | Значимость сигнала / feedback loop | Старт с фиксированного порога (вариант A из раздела 6.7), переход на адаптивный по мере накопления данных. Reliability scoring источников — да. Feedback loop — автоматический, силами AI, с рекомендованной ежемесячной выборочной проверкой человеком как контролем качества |
| 13.8 | Технический доступ к источникам | Гибрид: Bot API для добавленных вручную источников + осторожный клиентский доступ для автообнаружения новых. Курация — и ручная, и автоматическая одновременно |
| 13.9 | Объём сообщений / бюджет LLM | Каскад "дешёвый фильтр → дорогая модель только для подтверждённых кандидатов", детальный расчёт в разделе 6.7. Предварительная лёгкая фильтрация до LLM — да |
| 13.10 | Монетизация Market Intelligence | Отдельный платный add-on (не входит в базовый тариф) |
| 13.11 | Ценообразование по вертикалям | Уточнённый вопрос: если клиенты отслеживают разное число вертикалей (кто-то только Gambling, кто-то Gambling+Crypto+Nutra) — единая цена на весь add-on для всех, или цена зависит от числа отслеживаемых вертикалей? Вариант A (плоская цена) проще для MVP; вариант B (по числу вертикалей) точнее отражает ценность, но сложнее в биллинге. Рекомендация: старт с варианта A, пересмотр после MVP |
| 13.12 | Метрики успеха MVP | Статистику и точность прогнозов анализирует сам AI (feedback loop, 13.7) |
