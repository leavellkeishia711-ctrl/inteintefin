FinanceIntel: поэтапный план развития


0. Главная цель проекта


FinanceIntel должен стать операционной финансовой системой для медиабаинговых агентств, а не просто отчётным дашбордом.



Система должна отвечать на четыре разных вопроса:



Что произошло в рекламе?

spend;
revenue;
ROI;
ROAS;
кампании;
аккаунты;
байеры.
Сколько компания реально заработала?

подтверждённая выручка;
расходы;
payroll;
overhead;
EBITDA;
net profit.
Сколько денег доступно прямо сейчас?

банковские остатки;
деньги на рекламных аккаунтах;
hold;
ожидаемые выплаты;
фактически полученные средства;
обязательства.
Что нужно сделать дальше?

остановить убыточную кампанию;
не увеличивать бюджет;
подготовить выплату;
пополнить рекламный баланс;
сократить расход;
отложить выплату;
запросить подтверждение владельца.


Финальная версия должна быть не «AI, который смотрит на цифры», а системой:



данные → расчёт → контроль → рекомендация → согласование → действие → проверка результата


1. Жёсткие правила проекта


Эти правила нельзя менять ради скорости, удобства или красивой демо-версии.



1.1. Деньги всегда считаются через Decimal


Нельзя использовать float для:



доходов;
расходов;
зарплат;
курсов валют;
комиссий;
ROI;
ROAS;
балансов;
налогов;
выплат;
денежных лимитов.


Правильно:



Decimal("100.25")


Неправильно:



100.25


Причина простая: финансовая система не имеет права терять копейки из-за округления бинарных чисел.



1.2. Источник истины для P&L, transactions


P&L считается из финансовых транзакций:



transactions → P&L → EBITDA → Net Profit


campaign_run_stats используется для:



рекламной аналитики;
spend;
revenue;
ROI;
ROAS;
сравнения кампаний;
оценки байеров.


Но статистика рекламного запуска не должна автоматически становиться бухгалтерской транзакцией без явного правила происхождения.



Иначе одна и та же сумма может случайно попасть в P&L дважды.



1.3. Рекламный результат не равен прибыли


Нельзя показывать пользователю:



revenue - spend = чистая прибыль


Честная формула:



Net Profit =
Confirmed Revenue
- Ad Spend
- Consumables
- Payment Fees
- Direct Campaign Costs
- Payroll
- Overheads
- Taxes
- Other Financial Costs


1.4. Прибыль не равна доступным деньгам


Нельзя считать деньги в hold доступными для новых расходов.



Нужно разделять:



Booked Revenue
Confirmed Revenue
Expected Payout
Paid Revenue
Available Cash


Каждая цифра отвечает на свой вопрос.



1.5. Все данные принадлежат tenant


Каждая компания имеет свой company_id.



Нельзя:



принимать company_id из тела запроса;
принимать company_id из query-параметра для финансовых операций;
доверять company_id, присланному frontend;
передавать в AI данные без фильтра текущей компании;
выполнять финансовый raw SQL без tenant-контекста;
разрешать агенту обходить RLS.


1.6. RLS остаётся последней линией защиты


В проекте должны одновременно существовать:



PostgreSQL RLS;
tenant-контекст транзакции;
ORM-фильтрация;
тесты cross-tenant isolation.


ORM-защита не заменяет RLS. with_loader_criteria может не покрыть raw SQL, bulk update или нестандартный путь доступа.



1.7. Никаких секретов в коде и логах


Нельзя коммитить:



пароли;
JWT secret;
Supabase URL с паролем;
Telegram tokens;
рекламные API keys;
номера карт;
PAN;
полные платёжные идентификаторы;
банковские реквизиты;
реальные персональные данные.


В логах должны быть:



request_id
company_id в обезличенном виде
entity_id
operation
result
error_code


Но не секретные значения.



1.8. Каждый финансовый write должен быть аудируемым


Любое изменение должно оставлять след:



кто сделал;
когда;
что изменил;
какой объект затронут;
какой был старый статус;
какой стал новый статус;
какой request ID;
через какой источник выполнено действие;
был ли это человек, автоматизация или AI.


1.9. AI никогда не получает широкие права по умолчанию


AI не должен иметь универсальный доступ вида:



execute_any_sql
delete_anything
send_any_payment
change_any_balance


Каждое действие должно быть отдельным инструментом с:



чёткой схемой входных параметров;
проверкой tenant;
проверкой роли;
ограничением суммы;
идемпотентностью;
audit log;
возможностью отката или компенсации;
approval gate для опасных действий.

5. Этап 3. Довести мультитенантную безопасность


Цель


Исключить возможность утечки финансов одной компании другой.



Что реализовать


PostgreSQL слой


Для каждой tenant-таблицы:



ENABLE ROW LEVEL SECURITY
FORCE ROW LEVEL SECURITY


Политика должна проверять текущую компанию:



company_id =
NULLIF(current_setting('app.company_id', true), '')::uuid


Нужно использовать:



USING для чтения/изменения существующих строк;
WITH CHECK для INSERT/UPDATE.


Application слой


Tenant context устанавливается:



после проверки JWT;
внутри транзакции;
из user.company_id;
через ContextVar;
с обязательным reset(token) в finally.


ORM слой


Для ORM-запросов используется with_loader_criteria.



Если tenant context отсутствует:



не возвращать все строки


а бросать ошибку.



Raw SQL слой


Raw SQL разрешать только:



в явно системных сервисах;
через проверенную tenant session;
с ручным tenant-фильтром;
с тестом, подтверждающим RLS.


Обязательные тесты


tenant A не видит данные tenant B;
tenant A не может вставить строку tenant B;
tenant A не может обновить строку tenant B;
tenant A не может удалить строку tenant B;
raw SQL не обходит RLS;
запрос без ContextVar не выполняется;
app_user не имеет BYPASSRLS;
роли не владеют доменными таблицами;
parallel requests не смешивают ContextVar;
Celery task не наследует чужой tenant context.
Definition of Done


Ни один новый endpoint не считается готовым без теста tenant isolation.

domain;
tracker;
hosting;
SMS;
verification;
service;
account;
other.


Формула:



cost_in_base = cost × fx_rate_to_base


Расходник должен создаваться вместе со связанной транзакцией типа expense и категории consumable, либо через безопасный двухфазный процесс с гарантией идемпотентности.

Если расходник общий:



overhead += consumable_cost


Для долгоживущих сервисов предусмотреть распределение стоимости по периоду использования:



daily_cost = total_cost / number_of_active_days
allocated_cost =

Definition of Done

стоимость переводится в базовую валюту;
есть CRUD;
есть защита от PAN;
есть тесты на Decimal, валюту, tenant isolation и двойное списание;
расход отражается в P&L и экономике аккаунта.

9. Этап 7. Реализовать Partner Payouts и жизненный цикл дохода


Цель


Разделить потенциальный доход, подтверждённый доход, холд и фактически полученные деньги.



Жизненный цикл


booked → in_hold → scrubbed → approved → paid


Дополнительные статусы:



partially_paid
disputed
cancelled
written_off


Для выплаты хранить:



партнёрскую сеть;
кампанию;
campaign run;
период;
booked amount;
expected amount;
scrubbed amount;
actual amount;
валюту;
курс;
статус;
ожидаемую дату выплаты;
фактическую дату выплаты;
связанную транзакцию;
внешний ID;
причину корректировки.


Правила


booked не считается доступными деньгами;
in_hold не увеличивает Available Cash;
scrubbed уменьшает ожидаемый доход;
paid создаёт или связывает входящую транзакцию;
повторное получение одной выплаты должно быть идемпотентным;
изменение статуса должно попадать в Audit Log;
нельзя напрямую менять actual_amount без разрешения и истории изменений.


Definition of Done


реализован state machine;
запрещены недопустимые переходы;
есть обработка частичных выплат;
есть сверка с transactions;
есть тесты повторной обработки;
есть отчёт по hold и ожидаемым выплатам.
